# Decisions.md — Clarity

## Why decisions were made, what alternatives were rejected, and the reasoning behind each choice.

---

### 1. Three-agent multi-agent architecture
**Decision:** Three specialized agents (ClauseExtractor → PlainTranslator → RiskAdvisor) running in a pipeline.
**Rejected:** Single monolithic LLM call that does everything at once.
**Why:** Separating concerns makes each agent testable, replaceable, and allows the pipeline to degrade gracefully — if the LLM is unavailable, individual agents fall back to rule-based logic while others keep working.

---

### 2. Rule-based fallback for every agent
**Decision:** Every agent has a complete rule-based implementation that works without any API key.
**Rejected:** Requiring an LLM API key as a hard dependency.
**Why:** This project must be usable by non-technical people who may not have an OpenAI API key. The rule-based mode provides meaningful (if less nuanced) results with zero external dependencies. Users with an API key get richer LLM-powered analysis.

---

### 3. CLI-first, not web-first
**Decision:** Command-line interface with `--file`, `--text`, and `--interactive` flags.
**Rejected:** Building a web UI or API server as the primary interface.
**Why:** CLI is faster to build, easier to test, and works headlessly (server/VPS environments). A web UI can be added later as a separate layer — the core pipeline is interface-agnostic.

---

### 4. JSON internal data format
**Decision:** All agent outputs are Python dicts with a consistent schema; final output is available as JSON or Markdown.
**Rejected:** Proprietary binary format or pure Markdown throughout.
**Why:** JSON is language-agnostic, easy to debug, and allows other tools to consume Clarity's output programmatically. Markdown is the human-readable presentation layer on top.

---

### 5. `openai` package as optional dependency
**Decision:** `openai` is in `requirements.txt` but not imported at module level — imported only inside methods when API key is provided.
**Rejected:** Making `openai` a required dependency or using a different HTTP client.
**Why:** The project must install and run without any API calls. Late binding of the import means the package doesn't even need to be installed for rule-based mode.

---

### 6. LLM prompt design: strict JSON-only responses
**Decision:** Every LLM prompt instructs the model to return ONLY valid JSON, with markdown fences stripped in post-processing.
**Rejected:** Allowing free-form text responses and parsing them.
**Why:** Structured JSON output is parseable, predictable, and eliminates the need for fragile regex parsing of LLM prose. The post-processing strips code fences as a safety net.

---

### 7. Risk scoring: 0.0–1.0 scale
**Decision:** Risk scores are floats from 0.0 (safe) to 1.0 (dangerous), with thresholds at 0.4 (medium) and 0.7 (high).
**Rejected:** Categorical labels only (low/medium/high) or a 1-10 scale.
**Why:** A continuous float allows nuanced comparison between clauses. The thresholds are documented in `config.py` and can be tuned per use case.

---

### 8. Predefined clause types (16 types)
**Decision:** A fixed taxonomy of 16 clause types (payment, termination, auto-renewal, arbitration, etc.).
**Rejected:** Dynamic/emergent classification or free-text labeling.
**Why:** Fixed types make the output predictable for users and allow the RiskAdvisor to apply targeted checks per type. The list covers the 95% case for consumer-facing documents.

---

### 9. Orchestrator handles report assembly
**Decision:** A separate `Orchestrator` class compiles outputs from all three agents into the final report.
**Rejected:** Each agent writing to a shared report object.
**Why:** The orchestrator owns the "merge" logic — aligning clause indices, computing summary statistics, and formatting output. This keeps agents stateless and focused on their single responsibility.

---

### 10. No persistent storage
**Decision:** Clarity processes one document per invocation and outputs to stdout or a specified file.
**Rejected:** Database storage, user accounts, document history.
**Why:** Adding persistence increases complexity, creates privacy concerns (legal documents are sensitive), and makes the tool harder to distribute. Users own their documents and outputs.

---

### 11. Questions-to-ask generated by RiskAdvisor, not hardcoded
**Decision:** Questions are dynamically generated based on which flags were raised.
**Rejected:** A static list of "always ask" questions.
**Why:** Dynamic questions are more relevant — if the contract has no auto-renewal, don't ask about it. The orchestrator caps output at 5 most relevant questions.

---

### 12. Rule-based risk patterns are curated, not exhaustive
**Decision:** 10 risk flag categories with carefully curated regex patterns.
**Rejected:** Trying to match every possible unfair term pattern, or using ML classification.
**Why:** A focused set of high-impact patterns (auto-renewal, binding arbitration, hidden fees) catches the most common consumer traps. Over-engineering the rule set would increase maintenance burden for diminishing returns.

---

### 13. Offline-first, API-as-upgrade
**Decision:** The default mode runs entirely offline with rule-based logic. LLM API is an optional enhancement.
**Rejected:** API-required or API-optional-with-limited-offline.
**Why:** The primary use case is a non-technical person who wants to understand a document NOW, not after setting up an API key. Offline-first removes every barrier to entry.

---

### 14. Single-file CLI, no framework
**Decision:** `main.py` uses only `argparse` from stdlib. No Click, Typer, or other CLI framework.
**Rejected:** Adopting a CLI framework for argument parsing.
**Why:** `argparse` is zero-dependency, well-known, and sufficient for the current interface surface. A framework would add a dependency for marginal benefit.
